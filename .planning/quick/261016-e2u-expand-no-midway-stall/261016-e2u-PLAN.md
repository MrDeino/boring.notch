**Expand path today (read already, verified):**
1. `OrchestratorExpand.setLevel(.expanded)` calls `grow()` -> `animate()`. `animate()` calls `syncWindow(size:)`, which grows the panel at once, outside the spring. Then it sets `vm.notchSize` in `withAnimation(.spring(response: 0.4, dampingFraction: 0.82))` plus a second `objectWillChange`, then calls `syncWindow` again. Then `expanded.insert(k)` publishes, which changes the level.
2. `OrchestratorExpandedView.onChange(of: expand.level(for: vm))` calls `levelChanged()`. That fades `contentOpacity` to 0 over `fadeOut` (0.08 s). A `Task` sleeps 0.08 s, then **with animations off it sets `shown = .expanded; held = slot`**, which is the hidden swap. It sleeps to `fadeInDelay` (0.28 s), then fades in over `fadeIn` (0.15 s).
3. At the swap, the whole column is laid out again at the expanded size. In `column(_:)`, `OrchestratorChatView(proseLineLimit: open ? 4 : nil, maxRows: 60, expanded: !open)` changes `proseLineLimit` and `expanded`. `ChatBlockRow` is Equatable on those, so all of the last 60 rows re-evaluate. Each `OrchestratorSelectableText` (an NSViewRepresentable with `sizeThatFits`, OrchestratorChat.swift ~line 1207+) re-measures its text at the new width with no line limit. Diff cards appear (`hasDiffCard` = expanded && canDiff). User rows change alignment and padding. Also built from scratch at the same moment: `OrchestratorRunsRail` (a ScrollView of up to 10 `OrchestratorRunCard`s, two usage bars with GeometryReader) and `terminalPill`.
4. 80 ms plus the Task hop plus the layout lands at about 90-130 ms, the exact window of the measured stall (jym: `stalls[at+ms]=92+58`, `128+37`; jump 0.20-0.26 at ~131-134 ms). SwiftUI springs are time-based, so a 40-60 ms main-thread block shows as a hold, then a jump of 20-25% of the travel.
5. Other things on the per-frame path worth checking for expand's high p95 (17-26 ms, 5-26 frames over 20 ms per run, so not only the swap): `.shadow(radius: 6)` on a growing 850x540 shape (ContentView mainLayout, mirrored in `FramesRoot`), and `onGeometryChange` -> `slot`/`held` on `OrchestratorExpandedView`.

**Harness facts (SnapFrames.swift):**
- `together()` computes `jump` (the biggest progress step between drawn frames). `TogetherResult.even` is `jump <= 0.12` for every gated transition.
- `FRAMES_ONLY=expand` limits reporting **and gating** to expand. The other steps still run so the chain stays valid.
- `FRAMES_MARK=1` puts a busy-spin marker before each step, so Time Profiler can tell the steps apart. `FRAMES_LOOP=1` repeats forever (for `sample <pid>` / `xctrace --attach`). `FRAMES_TRACE=1` prints per-frame shape, body, window, rootBody and scroll rows. `orchPerf` signposts `frame-stall` with the transition and time.
- At 120 Hz an undisturbed spring with response 0.4 / damping 0.82 moves about 0.04-0.05 of its travel per frame at peak speed. So 0.05 means "no dropped frame at peak". If the idle step shows a cadence near 16.7 ms (a 60 Hz display), say so in the SUMMARY, because the 0.05 limit then can't be met on that display.
- The `togetherSelfCheck` series (40 samples, cubic) has a max step of about 0.075. Keep the self-check on the 0.12 default; don't apply 0.05 to it.
- `run.sh --paint` prints `paint <name> longest main-thread gap Nms at Nms` per transition. Use it as a second, real-composited measure of the swap gap in expand.

**Other runs:** another run is adding live reply streaming to chat rows. Do not restructure `ChatBlockRow`, `OrchestratorChatView`'s row list, or `OrchestratorSelectableText`. Any change there is limited to a small additive change inside `sizeThatFits` (option E below), and only if the measurements prove it necessary.
