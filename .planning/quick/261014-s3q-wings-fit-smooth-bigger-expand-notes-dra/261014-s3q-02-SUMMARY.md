## Grow-frame clipping investigation (time-boxed, no code change kept)
Frames at grow 0/30ms (`transition-live-grow-30.png`) show every row, the composer pill and the user bubble cut off ~30pt on the left while the shape is still ~657 wide. Findings:
- Not a minimum-width problem: a static render with `vm.notchSize = 657x540` at the expanded level (`static-657.png`, temporary) lays out cleanly (column ~400pt, rows start at the normal padding, composer inside the shape). So the layout is correct at that width; the clipping only exists mid-animation.
- A debug print in the view body showed it is evaluated only twice per grow (g=578 then g=788); the column's width is not recomputed per spring frame, the intermediate frames are SwiftUI geometry interpolation of the already-final layout (column laid out at ~490-600 wide, wrapped for the final width), placed centred against the narrower animated frame.
- Tried: explicit column width from a GeometryReader (`g.size.width - rail - gap`) with `.leading` alignment and `.clipped()`. Frames were unchanged (rows still cut at the left), so it was reverted, as was a harness left-margin check (it fails by 100+pt on these frames and would only pass with a fix).
- Not tried: removing the spring on the column's frame (snap to final layout, only the shape animates) or `.drawingGroup`/`compositingGroup` on the column; both change the "reflow with the spring" behaviour. The offscreen harness cannot show real spring frames (no display link), so this should be judged in the running app before spending more on it.
