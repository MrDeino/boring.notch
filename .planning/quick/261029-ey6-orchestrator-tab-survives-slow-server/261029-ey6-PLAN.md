# Quick 261029-ey6: Orchestrator tab survives a slow or briefly unreachable serve

Root cause (verified): every POST is followed by `refresh(fresh: true)`, which GETs /api/chat + /api/state through
the manager session (3 s request / 5 s resource). A busy serve answers /api/state in 2-10 s, so the GET times out,
`load()` calls `applyOffline()`, which clears prompt, runs, live reply and flips the column to the full-screen
Offline view. A typed card answer then fails its checks and the card is gone. Separately, the SSE stream forces
`reset` on the first blocks event of every connection (and the poll's ~30 s full resync resets too), so the chat
is replaced by serve's last 80 blocks; three failed block fetches swap the rows for the chatTail fallback.

## Task 1: tolerate slow / failing requests (OrchestratorManager, OrchestratorPure)
- Manager session: 20 s request / 30 s resource (a refused connection still fails at once).
- `reconnecting` published flag + `failures`/`failingSince`; pure `goesOffline(everLoaded:failures:failingFor:)`:
  offline only before the first good load, or after >= 3 consecutive failures over >= 30 s. Any good GET or
  stream event clears both. `stale = offline || reconnecting`.
- Capsule shows "Reconnecting" while stale-but-not-offline; chat, runs and card stay as they were.
- All POSTs go through one `postCode` that records `lastPostUnreached` (URLError.cannotConnectToHost: never
  reached serve, nothing typed, resend safe) and counts it as a failure.
- Background-agents load at stream start no longer blocks the event loop.

## Task 2: sends are never lost or doubled
- Composer queue (store.drain): waits while `stale`; a send refused before reaching serve goes back to queued and
  is sent once serve answers again. Timeouts (ambiguous) still mark the row failed with Retry (no auto resend).
- Question card free text: if serve is unreachable when Enter is pressed, the card and text stay up with
  "Waiting for the orchestrator…", and the answer is sent once serve is back (still checked against the live
  prompt). Stale data never counts as landed/moved; `submitting` blocks a second Enter.

## Task 3: chat never cleared on reconnect
- SSE connects with `?since=<last block id>` when the store holds blocks; the first event then appends via
  `ingestSince` (shared with the poll path): no shared id -> full fetch, replace only if our last id is gone.
- Poll full resync replaces only if our last id is missing (else merges).
- Block fetch failures keep held rows (fallback only when empty).

## Task 4: verification + audit

- Snapshot harness `--slowmock` vs Tests/slow-mock.py (port 47999): 10 s /api/state does not go offline; server
  killed -> chat + card stay, typed answer kept; server back -> answer POSTed exactly once; stream reconnect
  sends `since` and the chat keeps its rows.
